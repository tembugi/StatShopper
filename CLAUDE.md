# Stat Shopper

This addon's spec. The shared rules in `../CLAUDE.md` come first: they hold every rule that isn't this addon's own and win on any conflict.

@../CLAUDE.md

Stat filters for the auction house: the player ticks stats in the auction house's own Filter menu, and a search shows only gear that raises every ticked stat (Match all) or, with Match any, at least one of them. Agreed with the user.

- Name "Stat Shopper" (the user's choice; `ADDON_TITLE`). "Find My Stats" until 1.0.2, which CurseForge published as `FindMyStats-v1.0.2.zip`. Folder, repo (`tembugi/StatShopper`, public; was `tembugi/FindMyStats`) and packages `StatShopper`. CurseForge project ID 1726374 (https://www.curseforge.com/wow/addons/stat-shopper). Design canvas: https://claude.ai/artifact/U3xXPZ79hi25vV1sm17YH6

## Look
- At the end of Blizzard's Filter dropdown, after the spacer Blizzard queues behind its last group, added with `Menu.ModifyMenu("MENU_AUCTION_HOUSE_SEARCH_FILTER")`: a title with `ADDON_TITLE` in the title's gold and `v<VERSION>` right-aligned on the same row in `DISABLED_FONT_COLOR`, attached as Blizzard's menu guide shows (agreed with the user for 1.0.0). Attached text already has the title's font, and the menu refuses `SetFont` on it (1.0.0 and 1.0.1 called it and raised an error each time the menu opened).
- Under the title, one row with two radios side by side: "Match all" (the default) and "Match any" (the user's choice, from a CurseForge user's request: Strength, Agility and Stamina ticked found nothing). The game has no text for these, so they are English in every language. Blizzard's menu has one element per row, so the row is a `CreateFrame` element with two buttons attached with `MenuTemplates.AttachBasicButton` (a plain `AttachFrame` button is hidden by the menu's reset after attaching: the first build showed an empty row), each drawn as Blizzard draws a menu radio (`MenuVariants.CreateRadio`: `common-dropdown-tickradial` and `common-dropdown-icon-radialtick-yellow`) with a menu button's highlight. A click moves the tick and leaves the menu open. Rejected: a checkbox ("Match any ticked stat" and similar wordings), a "Show gear with" submenu, sorting by how many ticked stats an item has (as a second sort it changes almost nothing, as the first it hides the cheapest item), a column for it, and "any" with no switch (the user needs all of them at times).
- Then one submenu per stat group with the game's checkboxes; every stat and group label is a game string (`STAT_CATEGORY_*`, `TRADE_SKILLS`, `ITEM_MOD_*_SHORT`, `RESISTANCEn_NAME`). Six groups, as on the canvas (agreed with the user): Attributes, Attack, Spell, Defense, Resistances, Professions (`TRADE_SKILLS`), with lines (`CreateDivider`) between sections of Attack and Spell. The list is `ns.STAT_GROUPS` in `Stats.lua`, one line per stat, the same for every player (a list that learns from each player's searches was rejected: every player must see the same menu). The user asks for new stats as they turn up; adding one is one line.
- Which stats (the user's rule): every stat seen on real Forever gear (the auction house, and a scan of every item the game had loaded: 52 stat names), every stat on Forever's character sheet (`Camelot/PaperDollFrameConstants.lua`: adds Armor Piercing), all 12 professions (vanilla's 9 + Cooking, First Aid, Fishing), and all 8 enemy types for Attack Power Vs and Spell Damage Vs (names only Forever's game text has). Out: Armor and damage per second (on almost every item), Health, Mana and movement speed (sheet totals, no item stat seen), modern stats (Versatility, Mastery...), split melee/ranged/spell Hit and Crit (Forever has one each), weapon skills, Jewelcrafting.
- Hit, Critical Strike and Haste count for melee and spells alike in Forever, so they are in Attack and in Spell: one key, ticked in both. "Attack", not "Melee": the group holds ranged stats too.
- No Spell Power entry: Spell Power gear ("Increases damage and healing done by magical spells and effects", Staff of Jordan, checked in game) counts for Spell Damage and for Spell Healing; ticking both finds only gear that raises both. Healer gear also carries a little spell damage ("of the Physician" adds healing and a little damage), so it counts for both too.
- A resistance has two names in the stat table (`RESISTANCE2_NAME` and `ITEM_MOD_FIRE_RESISTANCE_SHORT`, always together); only the first has a game string, so it is the label.
- The red X on the Filter button shows while any stat is ticked or Match any is chosen (also with nothing ticked: the user found it missing), as it does while Blizzard's own filters differ from their defaults; clicking it unticks the stats and goes back to Match all.
- Nothing else on screen and no chat lines in normal use.

## Filtering
Agreed with the user.
- With Match all, an item must raise every ticked stat; with Match any, at least one. Match any keeps the list's own sorting (Price or Name): items with more ticked stats aren't moved up. An item raises a stat with a positive amount under any of the stat's names in the game's stat table (`Stat(key, label, other names...)`). No minimum amounts.
- Ticks and the Match choice apply when a search is sent, like Blizzard's own filters: a search keeps the stats and the choice it was sent with (also when re-sorted), and changing them changes nothing until the next search.
- Favorites (the star button, and the list the auction house opens with) are never filtered, as Blizzard's filters don't apply to them. Both go through `AuctionHouseFrameMixin:QueryAll(AllFavorites)`, hooked: the ticks of the last search are dropped there. `isDisplayingFavorites` alone isn't enough: opening one of the favorites (`QueryItem`) clears it while the list behind is still the favorites, and an item's auctions arriving update the list (0.3.0 filtered the favorites).
- Saved: ticks and the Match choice (`matchAny`) per character, like the auction house's own filters (`SavedVariablesPerCharacter: StatShopperDB`); learned endings for the account (`SavedVariables: StatShopperAccountDB`, per game build: an update may change them).
- The server can't filter by stats, so the addon filters the browse results it gets. Each result is one item key: the item, its item level and its random ending ("of the Whale", the key's `itemSuffix`). Its stats are the item's own, from the game's stat table (`C_Item.GetItemStats("item:<id>")`, keyed by the `ITEM_MOD_*_SHORT` names the menu shows), plus what its ending adds. Never from a tooltip.
- Only weapons and armor can match (`C_Item.GetItemInfoInstant` class). Checked in game: a scan of every loaded item that isn't a weapon or armor found no menu stat; the only stat was damage per second on ammo (Projectile). Quivers' ranged attack speed isn't in the stat table.
- How the list changes: a `hooksecurefunc` on the results frame's `UpdateBrowseResults` takes each page of results into the search's collection (one entry per item key: item, item level, random suffix), hands the frame the matching ones (`browseResults`) and redraws its list (`ItemList:RefreshScrollFrame`).
- Rebuild only what the player would see. Every redraw of Blizzard's list rebuilds every row on screen: `RefreshScrollFrame` gives its scroll box a new data provider, and the scroll box releases and remakes all rows (`ScrollBoxListView`, no recycling for a replaced data provider). Blizzard's own list redraws only when a page arrives, which it asks for only as the player scrolls near its end; the addon once redrew up to four times a second while a search loaded, and the user's first click on a row sometimes did nothing (suspected: a rebuild between pressing and letting go; not measured in game). So the addon hands over its matches only when that changes what is on screen: a row on screen would show another result or price, or the list's end is less than 30 rows below the last row on screen (Blizzard's own number for asking for more, `BROWSE_SCROLL_OFFSET_REFRESH_THRESHOLD`) and more matches are ready. Matches further down show as the player scrolls toward them: the list calls the addon's check as its refresh callback, as it calls Blizzard's own to ask for pages. When a page arrives, Blizzard appends its raw results to the addon's list and marks the list for a redraw (`DirtyScrollFrame`); the addon takes them back out and clears the mark (`scrollFrameDirty`) unless it hands over. No rebuild while a mouse button is held over the rows (`IsMouseButtonDown`, `ScrollBox:IsMouseOver`): it waits until the button is let go. Rejected: holding redraws while the mouse is over the list (the list would stop filling in); the user asked for a better way, which is the rule above, and the mouse-button hold stays as its last guard.
- Every page: the server sends results in pages, and Blizzard's list asks for the next one only when fewer than 30 rows are left below the last one on screen. Filtering and sorting need them all, so after each page the addon asks for the next (`C_AuctionHouse.RequestMoreBrowseResults`) when the auction house's throttle is ready (`IsThrottledMessageSystemReady`, else `AUCTION_HOUSE_THROTTLED_SYSTEM_READY`), until `HasFullBrowseResults`. This continues the player's own search, as scrolling to the end would; the addon sends no browse searches of its own.
- One request at a time: Blizzard's list asks for more on every redraw and scroll while near its end, without waiting for the throttle, and a filtered list is always near its end. So while the addon's list is on screen, Blizzard's asking is off: the list's refresh callback is the addon's own check, which asks for nothing (Blizzard sets its own again with the next results, and `ShowAllResults` rebuilds the list through Blizzard's `UpdateBrowseResults`). 0.3.0 left it on: in the stand-in it asked for 6 pages where 4 were needed, and requests queued up.
- Paging and learning endings wait while the results list isn't on screen (`GetDisplayMode` not `Buy`: viewing an item, buying, another tab): the player's own requests go first. The worker asks again when the list is back.
- Never stalling: items are read within a 4 ms budget a frame (`FRAME_BUDGET`), and at most 30 items' data is asked for at a time (`MAX_ITEM_LOADS`). An item whose data isn't loaded waits for `ITEM_DATA_LOAD_RESULT`; one whose load fails stays out of that search.
- No tooltips: measuring builds found that the first tooltip in a session with the ending "of the Physician" (on several items) stalls the game for 14.2 s inside `C_TooltipInfo.GetItemKey`, in every session; hovering such a row in Blizzard's own list does the same. Reading the tooltip once to learn the ending was rejected by the user: the addon must never freeze anyone's game, not even once. The auction house's info on the item key (`C_AuctionHouse.GetItemKeyInfo`) gives the name the list shows and sorts by; an entry waits for `ITEM_KEY_ITEM_INFO_RECEIVED` until it has it, and a listing it can't name stays out of the results.
- Endings (found in game): a row's tooltip shows an ending's stats as ranges ("+low-high Intellect") or not at all ("of the Whale": none, "Items in this group may vary in stats"). The item key holds only the ending's number; the stats come with a bonus in each auction's real link. The stat table reads that link instantly, even for Physician (0.13 ms), but not a link built from the item key (the suffix in the seventh field changed nothing on 4877 items). An early check that "no ending adds stats" was wrong: it couldn't read ranges, and most rows' tooltips show none.
- Learning an ending (agreed with the user): the first time a search meets an ending the account hasn't learned, the addon asks the server for one row's auctions (`C_AuctionHouse.SendSearchQuery`, as clicking the row would) and reads one auction's real link: what the ending adds is what that link's stat table has beyond the item's own (`ns.EndingAdds`, every stat name, so stats added to the menu later need no new learning). An ending adds the same stats to every item. Requests go one at a time, behind the game's throttle and at least 0.7 s apart (the server allows 100 a minute), only while the results list is showing; a row the auction house has already searched needs none; a row with nothing to learn from (sold, or no answer in 10 s) gives way to another with the same ending, up to 3 per search. Until its ending is learned, an item matches by its own stats; the list grows as endings are learned. A whole-auction-house search learns every ending in it once (at 0.7 s each); a narrow one only its few.
- Sorting: the addon sorts the matches itself, by Blizzard's own sorts for the search (`GetSortsForContext(GetBrowseSearchContext())`: up to two of Price (`minPrice`) and Name (the item key's `itemName`), each possibly reversed), ties by arrival. A header click (`hooksecurefunc` on the results frame's `SetSortOrder`) sorts the matches at once; Blizzard's re-sent search merges in (fresher prices) instead of starting over, and once every page has arrived it fetches no pages again. (0.1.0 showed pages in arrival order and restarted on every re-sort, so the user never saw a sorted list.)
- Empty list: Blizzard's list shows "No results" once every page is in, even while the addon still reads items. Until the addon is done, it shows Blizzard's own loading spinner (`ItemList.LoadingSpinner`) in its place. Then the list sets its own look again (`ItemList.state = nil` and `RefreshScrollFrame`): its `SetState` skips a state it thinks it shows, so a guess by the addon could leave it blank.
- A new search (`SendBrowseQuery` hook), favorites or a closed auction house ends the collection; the addon only ever changes the list it handed over.

## Open: "No items found" on a search that has results
- First seen once: a search sent while the previous one was still loading showed nothing; searching again worked. The audit (0.3.1) then found the likely cause, Blizzard's own list asking for pages on top of the addon (see One request at a time): requests queued up (`AUCTION_HOUSE_THROTTLED_MESSAGE_QUEUED`, seen in game) and one could be dropped. That was fixed.
- Seen again after the fix, in the 1.2.0 test: on Armor, a Match all search with Strength, Agility and Stamina, then Match any, showed "No items found"; searching again found items. So the cause is still unknown. Blizzard's list shows that text only with no rows and the game reporting every page in, so either the search's results never came or the addon matched nothing.
- A measuring build (commits 7e11833 to 44e7b06 on branch match-any, reverted before release) recorded each search's throttle events, pages, the addon's requests and redraws, and sent the record to the error handler when a Match any or unfinished search ended in "No items found". The user couldn't reproduce it with it; its only record was a correct empty search (Melee Attack Power on armor: all 7,806 results in and read, none with the stat). If it comes back, revert the revert to get that build again.

## Taint
- The filtered list is the addon's table, so while it is on screen, Blizzard's results list and what a click on a row starts (the item's buy page) run tainted. Nothing in the auction house API is protected: `IsProtectedFunction` marks only widget methods, and `PlaceBid` and `StartCommoditiesPurchase` carry `HasRestrictions`, like `SendChatMessage`. Buying from a filtered list is the main thing to test: watch for "action blocked" and read `taint.log`. In the user's tests with taint logging on, buying worked and the game wrote no taint.log at all.
- The addon also writes the list's `state` (to make it set its own look again) and `scrollFrameDirty` (to cancel a redraw of a page it takes back out), and sets its refresh callback to an addon function, which the list calls as the player scrolls: all only touch the auction house list, which is never protected.
- The X follows Blizzard's rule by reading the Filter button (`GetFilters`, `GetLevelRange`), never by calling `UpdateClearFiltersButton`, which writes Blizzard's saved filters.

## Errors
- When the auction house loads, the addon checks the Blizzard pieces it plugs into. If one is missing, it says so once (with its version) and adds nothing.
- Every hook and handler runs through `Guarded` (the shared error rule). After the first error the search's full list goes back on screen, and the filters stay off until /reload.

## Tests
`luajit Tests/run.lua` checks the rules in `Stats.lua`: the stat list (labels, dividers, a stat in two groups the same in both), Spell Power counting for Spell Damage and Spell Healing, a resistance under either name, reading stats from the stat table with and without an ending, what an ending adds, the all-of and any-of rules, telling results apart, sorting like the browse list, the ticks a search keeps, `NormalizeSaved` and `NormalizeAccount`. Their items, endings and names are made up, shaped like what the game gave.

`StatShopper.lua` plugs into Blizzard's code and is tested in game and in the stand-in, `Tests/standin.lua` (run by `run.lua`, one luajit per scenario): Blizzard's auction house code the addon touches, copied from `wow-ui-source` (results list and its state, its rows on screen and their rebuilds, its own asking for pages, search, favorites, item view, sorting), and a simulated server (pages of 50, one request at a time with a queue, slow item data, a row's auctions with real links). `QUEUE_SIZE` (how many requests may wait) is unknown in game, so the second-search scenarios run with 1 and 3. Scenarios: the list stays still (no rebuild while the player looks at the top of a long list, the rest shows on scrolling down, no row moves; ASSUMED: the server sends results in the sort's order), clicks are never lost (a player pressing rows again and again while a short list fills in), the menu's title, the Match row (two choices side by side inside the row, built only from what Blizzard's menu attaches; a click moves the tick; the red X goes back to Match all), Match any against Match all on the same search, one request at a time, paging waits while viewing an item, favorites stay unfiltered, re-sort without fetching again, an error puts the list back, and a second search at 30 moments of the first. The released 0.3.0 fails the first four. `TRACE=1` logs what the list shows each frame.

## Never
- Never replace a Blizzard function or the results frame's data provider.
- Never send requests of its own except these two, both paced: the next page of the player's own search, and one row's auctions to learn an ending the account hasn't seen.
- Never change Blizzard's saved filters (`g_auctionHouseFilters`).
- Never call anything that builds a tooltip (`C_TooltipInfo`, `GameTooltip`): see No tooltips.

- The Buy button after the game's: black edge, thin grey ring, black gap, flat dark red face, gold text in regular weight.
